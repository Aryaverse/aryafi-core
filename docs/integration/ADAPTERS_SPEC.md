# Custodial & Settlement Rail Adapter Specifications

## 1. Overview & Architecture

The **AryaFi Adapter Layer** provides institutional-grade, fault-tolerant bridging microservices connecting external market rails (Fedwire, SWIFT, DTCC, Euroclear, Core Banking) to Canton participant nodes running the AryaFi Daml smart contract library.

The adapter architecture enforces a strict **separation of concerns**:
- **Daml Smart Contracts**: Sole authority over rights, encumbrance states, compliance gating, and atomic multi-party state transitions.
- **Adapter Microservices**: Handle protocol serialization (ISO 20022 XML, FIX, JSON), network transport (SWIFT Alliance Gateway, MQ Series, Kafka), mTLS authentication, and asynchronous settlement triggers.

## 2. Core Rail Adapter Implementations

### 2.1 Fedwire Funds / RTGS Adapter (`FedwireAdapter`)

The `FedwireAdapter` manages institutional cash legs over the Federal Reserve Fedwire Funds Service.

#### Ingress Workflow (Fedwire Credit Received):
1. Fedwire Funds terminal emits an incoming transfer notification containing an **Input Message Accountability Data (IMAD)** identifier:
   - Format: `YYYYMMDDABCD000001` (22 characters).
2. `FedwireAdapter` intercepts the notification, parses the debtor and creditor accounts, and queries the Canton Active Contract Set (ACS) for a matching `PaymentInstruction` where:
   - `payerAccountId` matches debtor account.
   - `payeeAccountId` matches creditor account.
   - `amount` and `currency` match the wire transfer amount.
3. If found and in `PendingSettlement` status:
   - Exercises choice `AttachNetworkRef` with `PaymentNetworkRef(IMAD)`.
   - Exercises choice `ConfirmPaymentSettlement` to transition payment to `Settled`.
   - Updates the associated `CashPosition` balances atomically.

#### Egress Workflow (Outbound Fedwire Submission):
1. `PaymentInstruction` created on ledger with `purpose = GeneralPayment` or `LoanDisbursement`.
2. Egress consumer detects `CreatedEvent` on `PaymentInstruction`.
3. Validates that `settlementAgent` is the bank's participant node.
4. Generates a Fedwire ISO 20022 `pacs.009.001.10` message and dispatches it over the Federal Reserve Depository Institution Testing (DIT) / Production connection.

### 2.2 SWIFT Alliance Gateway Adapter (`SwiftAdapter`)

The `SwiftAdapter` connects institutional counterparties executing cross-border capital mobility and intercompany netting over the SWIFT network.

#### End-to-End Tracing with SWIFT UETR:
- Every payment carries a mandatory **Unique End-to-End Transaction Reference (UETR)** (RFC 4122 UUIDv4) generated by the instructing debtor.
- The `SwiftAdapter` binds this UETR to the `PaymentInstruction.networkRef` field.
- When an intermediate correspondent bank updates status (e.g., via `pacs.002` Payment Status Report), the adapter updates internal telemetry and reflects rejections via `RejectPaymentSettlement` if flagged for AML/sanctions.

### 2.4 Compliance & AML Screening Adapter (`AmlKycAdapter`)

The `AmlKycAdapter` automates the onboarding and continuous screening gates required by AryaFi's `Compliance` layer.

#### Interfaces:
1. **KYC Verification Feed**: Ingests verified institutional client profiles from enterprise KYC hubs (e.g. Fenergo, Encompass).
   - Issues on-ledger `KycAttestation` contracts with expiry timestamps and verified jurisdictions (`UpdateKycStatus` records ledger time as the verification time).
2. **Sanctions Screening Engine**: Connects to real-time screening services (e.g. LexisNexis Bridger, Accuity, Fircosoft).
   - Ingests OFAC, EU, and UN sanctions updates.
   - Exercises `RevokeKyc` on the `KycAttestation`, or `BlockParty` / `UpdateSanctionsStatus` on the `SanctionsAttestation`, when an active counterparty is flagged.

## 3. High Availability, Idempotency & Fault Tolerance

### 3.1 Idempotency Guarantee Pattern
To eliminate double-execution risks during adapter failover or network retries:
1. All inbound payloads must carry an idempotency key (e.g., SWIFT UETR or Fedwire IMAD).
2. The adapter executes an atomic Redis `SET NX EX` command with a 24-hour TTL:
   ```python
   # Atomic Redis Deduplication Lock
   lock_acquired = redis_client.set(f"idemp:{idempotency_key}", "IN_PROGRESS", nx=True, ex=86400)
   if not lock_acquired:
       # Duplicate event detected -> return cached response or log duplicate
       return fetch_existing_submission_status(idempotency_key)
   ```
3. Once the command is committed to Canton, the Redis status is updated to `COMMITTED` with the resulting transaction ID.

### 3.2 Dead Letter Queue (DLQ) & Circuit Breaking
- Inbound messages that fail business validation or contain malformed payloads are routed to an enterprise Dead Letter Queue (`dlq.inbound.payments`) for operator inspection.
- The adapter integrates a **Hystrix / Resilience4j** circuit breaker:
  - If the Canton Ledger API error rate exceeds 50% over a 10-second rolling window, the circuit trips to `OPEN`.
  - Inbound messages are safely buffered on the message bus without dropping connections to external market rails.

## 4. Security & Network Isolation

1. **Mutual TLS (mTLS)**: All connections between Adapter microservices and Canton Ledger API endpoints enforce TLS 1.3 with mandatory client certificate verification (X.509 certificates issued by internal enterprise PKI).
2. **Hardware Security Module (HSM) Signing**: Where multi-signatory proposals require adapter signing authority, private keys are safeguarded within FIPS 140-2 Level 3 HSMs or AWS CloudHSM / Azure Dedicated HSM.
3. **Audit Logging**: Every inbound and outbound message is logged with its SHA-256 digest, correlation ID, and network reference in tamper-evident append-only storage.
