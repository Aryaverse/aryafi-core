# Known Limitations

This page records what AryaFi Core does **not** do yet, so that nobody builds on an assumption the code does not support. It is required by the *Definition of Done — Production Module* (Technical & Business Requirements §21, §30) and is updated with every release.

Last reviewed: 2026-10-24, against the code for 3.4.0 (in development).

---

## 1. Maturity Status

Maturity labels follow [VERSIONING_AND_RELEASE.md](governance/VERSIONING_AND_RELEASE.md#2-module-maturity-levels). No module has had an independent security review, so none is `Production Candidate` or `Production Reviewed`.

| Module | Status | Why |
|:---|:---|:---|
| `Common.*` (Types, Identifiers, Time, Errors, Policies, Events) | Beta | Used by all modules and unit-tested; day-count conventions verified against ISDA examples. |
| `Finance.Cash`, `Finance.Security`, `Finance.Asset` | Beta | Lock-holder model, receiver-authorized transfers, and split/merge are tested, including negative and privacy tests. |
| `Finance.Settlement` (DvP) | Beta | Atomic Model 1 DvP moves real positions and is tested for leg mismatch, lock integrity, retry, and cancellation. |
| `Finance.Account`, `Finance.Party`, `Finance.Obligation`, `Finance.Payment`, `Finance.Collateral` | Experimental | State records; not yet linked to the positions they describe. |
| `Contracts.*` (Loan, Repo, ReverseRepo, SecuritiesLending, Margin, Pledge, Escrow, Transfer, Subscription, Redemption) | Experimental | Lifecycle state machines with corrected authorization. Loans, repos, securities loans, pledges, collateral, and margin calls can move their cash and securities on the ledger; escrow, subscriptions, and redemptions do not yet (see §3). |
| `Compliance.*` | Experimental | KYC, sanctions, transfer rules, and ownership restrictions are evaluated inside token-standard transfers and allocations, the screened DvP, and screened asset transfer requests (`Compliance.Gate`); the policies are simplified, and eligibility policies and jurisdiction profiles cannot be called from workflows yet (see §4). |

## 2. Platform

- **Daml 3 / Canton 3.5.** The DAR targets Daml-LF 2.2 (Daml SDK 3.5.12) and is tested on Canton 3.5.19 with protocol version 35. It does not run on Canton 2.x. It has not yet been deployed to the Canton Network; [deploy/testnet](../deploy/testnet/README.md) has the smoke test and runbook for a first TestNet run (TestNet runs Canton 3.5.18 as of 2026-09-30).
- **Token standard: holdings, transfers, settlement, and DvP; not yet tested with Canton Coin.** Cash, securities, and asset positions implement the CIP-56 and CIP-0112 `Holding` interfaces, so wallets and apps can list them. Cash and securities can also be sent with the CIP-0112 transfer interfaces (`TransferInstructionV2`), through the bank's or custodian's `PositionTransferFactory`, and settled with its allocation interfaces (`AllocationV2`), through its `PositionAllocationFactory`. `TokenDvpInstruction` settles a DvP through allocations at any V2 registry. Not done yet:
  - a DvP against Canton Coin itself: the tests settle against Splice's reference V2 token (`splice-test-token-v2`) and AryaFi's own registries. Canton Coin's registry implements the same interfaces, but needs the choice context and disclosed contracts from its off-ledger API, which only a Canton Network deployment provides;
  - iterated settlement (`nextIterationFunding`) and allocation instructions that wait for approval (AryaFi allocations are created at once). By design, an AryaFi allocation settles only through its registry's `SettlementFactory_SettleBatch`; `Allocation_Settle` on a single allocation is refused;
  - the V1 transfer and allocation interfaces: a wallet that supports only CIP-56 V1 can list AryaFi positions but not send or settle them;
  - transfers and allocations of `AssetHolding`, whose admin (the issuer) cannot move a holding without the custodian;
  - the registry's off-ledger API (instrument metadata, factory lookup, choice context, disclosed contracts) and the V2 transaction-history events (`TransferEventsV2`). Instead, AryaFi's factories are shown on the ledger to the registry's clients, and wallets find them with an interface query.
- **Pending transfers and allocations are visible to the other side.** While a token-standard transfer waits for acceptance, the receiver sees the sender's locked holding, because the receiver's participant needs it to accept. A holdings query for the receiver returns it, so wallets should list a party's holdings by account owner. Likewise, a settlement's executors see its allocations and their locked funding, which a holdings query for an executor returns.
- **No uniqueness guarantees.** Daml-LF 2.2 has no contract keys, so the ledger does not stop a second `Account` with the same custodian and account ID, a second `KycAttestation` or `SanctionsAttestation` for the same authority and subject, or a second `TransferRestrictionRule` or `OwnershipRestriction` for the same ISIN. The issuing party must check its active contracts before creating one.
- **Upgrades are checked by Canton.** Canton 3 validates every package with the same name (`aryafi-core`) as an upgrade of the versions already on the participant. A release that changes templates incompatibly must use a new package name or a separate participant. CI checks every build against the latest release's DAR, with the participant's upgrade checks and the compiler's; the compiler is told to allow, and report, interface instances added to existing templates, a supported upgrade it otherwise refuses. Interfaces that AryaFi's templates implement live in their own package (`aryafi-compliance-api`), because an interface cannot be upgraded together with its implementations.

## 3. Composition and Asset Movement

- **DvP and the financing contracts move assets; transfer requests do not.** `ExecuteDvpSettlement` delivers locked `SecurityPosition` and `CashPosition` contracts atomically, and `ExecuteTokenDvp` settles both legs of a token-standard DvP at their registries in one transaction. Locked pledges and collateral hold their positions until release, enforcement, or liquidation, and a margin call paid by transfer receives the cash as it is satisfied. A loan's drawdowns and repayments can be token-standard transfers that the receiver accepts as the loan records them (`DrawdownByTransfer`, `ReceiveRepayment`). A repo's opening and closing legs, and a securities loan's delivery and returns, can be token-standard DvPs that the custodian settles through the agreement (`SettleOpeningLeg`, `SettleClosingLeg`, `SettleDelivery`, `SettleReturn`). An escrow can hold its deposit, locked to the agent, and deliver or unlock it (`DepositIntoEscrow`, `ReleaseEscrow`, `RefundEscrow`). The custodian can settle a capital call by issuing units against the investor's cash, and a redemption by burning units against the payout (`SettleCapitalCall`, `SettleRedemption`); it must see the cash transfer, as the fund's depositary bank or by disclosure. A payment instruction can execute as a token-standard transfer (`ExecutePayment`). A securities loan with a fee accrual computes its fees and rebates on the ledger, and they are paid by transfer (`ReceiveLendingFee`, `ReceiveRebate`). Each of these still has its older choice that records a movement settled elsewhere. `AssetTransferRequest` records lifecycle state only, and a securities-lending return that releases no collateral is a separate transfer. An escrow's release and refund, like a pledge's enforcement, move the locked position directly, without the bank's compliance checks.
- **References are text, not contract IDs, except for locked pledges, collateral, escrow deposits, and transfers.** A pledge can hold the pledged cash or security position, locked to the pledgee (`EncumberHolding`), and a collateral position its security position, locked to the receiver (`LockCollateralHolding`), so neither can be locked twice; release, enforcement or liquidation, and substitution act on the locked position. An escrow holds its deposit's locked position (`escrowedHoldingCid`). A margin call, a loan, a capital call, a redemption, and a securities loan's fees and rebates can be paid by a token-standard transfer that the receiver accepts as the contract records it. Pledges and collateral that are not locked, margin paid by `SatisfyWithCash` or `SatisfyWithPledge`, and movements recorded as settled elsewhere identify assets and payments by text reference, so the ledger does not stop one asset being referenced by several agreements. `AssetHolding` positions cannot be locked this way, because the token-standard helpers cover cash and securities only.
- **Exact-size legs.** A `DvpInstruction` leg must match the instructed quantity or amount exactly; split the position first. (A token-standard allocation locks the exact amount from larger holdings itself.) Partial settlement is not supported.
- **Netted settlement.** `DvpModel2` and `DvpModel3` exist as reference data; only Model 1 executes.
- **Failed or cancelled DvP.** For a `DvpInstruction`, both legs stay locked to the settlement agent, who must release them with `UnlockSecurity` / `UnlockCash`. For a `TokenDvpInstruction`, cancelling cancels the allocations the agent passes, and the parties can withdraw the rest.

## 4. Multi-Party Workflows and Compliance

- **Across participants, multi-party steps go through proposals.** A `MultiPartyProposal` (`AryaFi.Contracts.Proposal`) collects signatures one party at a time, so parties on different participants can create every AryaFi contract with several signatories and exercise every choice that several parties control. Without a proposal, these steps still need all their parties in one submission (`submit (actAs [...])` in Daml Script, several `actAs` parties on the Ledger API). Proposals have no expiry date: a signer withdraws or rejects one that is no longer wanted. Cash and securities move between participants through token-standard transfers, not proposals; an `AssetHolding` transfer works through a proposal only if the new owner, who cannot yet see the holding, is not the last to sign. `runDvpAcrossNodes`, `runTokenDvpAcrossNodes`, `runFinancingAcrossNodes`, and `runFinancingLegsAcrossNodes` run the reference DvP, the token-standard DvP, a repo and an escrow agreed and changed, and a repo's legs and a funded escrow settled, on the `deploy/` topology with each institution on its own participant, locally and in CI. The last signer of a joint choice that moves a locked position must see it: for an escrow's release, the agent, which holds the lock.
- **Compliance inside transfers, allocations, and DvP.** KYC attestations, sanctions attestations, transfer restriction rules, and ownership restrictions implement the `CompliancePolicy` interface (package `aryafi-compliance-api`), which any party that sees the contract can evaluate. A bank or custodian sets `ComplianceRequirements` on its `PositionTransferFactory` or `PositionAllocationFactory`, and a `DvpInstruction` or `AssetTransferRequest` can carry them; `AryaFi.Compliance.Gate` then evaluates the evidence the caller passes, in the same transaction, and records each decision as an `AuditLog`. What it does not do yet:
  - eligibility policies and jurisdiction profiles do not implement `CompliancePolicy`: their asset classes are free text, which no instrument carries, so no workflow evaluates them;
  - an ownership restriction checks the receiver's jurisdiction (from its KYC attestation) and the transferred amount against the holding limit, but not what the receiver already holds, because positions are not aggregated on the ledger, nor the percentage limit, because the ledger does not hold the issue size;
  - the financing contracts (loans, repos, securities loans, pledges) do not evaluate compliance. An `AssetTransferRequest` without requirements still needs the compliance officer's `ApproveTransfer`;
  - the evidence is what the caller passes. Missing evidence is refused, but the gate cannot tell that a party has a second, worse attestation, or that a rule by another accepted officer was left out. Evidence is never stale: an authority changes an attestation or rule by archiving it, and an archived contract cannot be evaluated;
  - an allocation is screened when it is made, not again when its batch settles (a failing check there could only abort the whole settlement); a pending transfer is screened again when the receiver accepts it;
  - a manual-review decision (a flagged screening, a restricted category without a whitelist, a holding period, an unknown jurisdiction) refuses a token-standard transfer, allocation, or DvP; only a screened `AssetTransferRequest` is left with the compliance officer to approve or reject.
  - financing payments made by transfer (loans, margin calls, capital calls, redemptions, lending fees and rebates) and executed payment instructions go through the registry's factory and are screened; a locked position delivered or unlocked directly, by a pledge's enforcement, a collateral liquidation, or an escrow's release or refund, is not.
- **Simplified policies.** `EvaluateTransfer` maps regulatory categories to investor flags supplied by the caller; it is not legal advice. Evaluated through `CompliancePolicy`, a transfer rule has no investor flags: it approves a receiver on its whitelist, refers a restricted category without a whitelist to manual review, and cannot check a holding period, because positions do not record when they were acquired. `EligibilityPolicy.minCreditRating` is stored but not evaluated. Asset classes are free text rather than the `AssetClass` type. `OwnershipRestriction` percentages are supplied by the caller, not computed from holdings. `JurisdictionProfile` has no effective dates.
- **Identifiers are not validated on-ledger.** ISIN, CUSIP, and LEI values are wrapped in newtypes but their check digits are not verified by any template.

## 5. Financial Semantics

- **Interest is computed only for loans.** `InstitutionalLoan` accrues interest from rate, day count, and ledger time. Securities-lending fees are agreed by both counterparties; the rebate rate is stored but not applied. Repo repurchase prices are agreed, not checked against the repo rate.
- **Day counts.** Act/360 and Act/365F count elapsed 24-hour periods between timestamps; Act/Act ISDA and 30/360 (US Bond Basis only) use UTC calendar dates. There is no business-day calendar or date adjustment.
- **Rounding.** Amounts use Daml `Decimal` (10 decimal places). The `RoundingMode` type exists but no calculation applies a currency-specific rounding convention.

## 6. Integration and Operations

- **Idempotency keys are stored, not enforced.** Use the Ledger API command ID and deduplication period for idempotent submission.
- **Audit events are emitted for compliance decisions only.** The compliance gate records an `AuditLog` for every decision it makes. Otherwise `AuditLog` and `RegulatoryReportRecord` contracts are created by the reporting party; no workflow emits them on settlement.
- **Local test topology only.** `deploy/` runs five in-memory Canton 3.5 participants and one synchronizer (sequencer and mediator) for integration testing. The config and bootstrap script have been run against Canton 3.5.19, and the DvP scenario and test suites (`runTreasuryDvpScenario`, `runDvpSettlementTests`) pass with `dpm script` against one of its participants. CI builds the Docker image, boots the topology, and runs both suites against it on every push and pull request (`canton-topology` job). Scripts that call `setTime` only run on the test ledger.
- **No field filters on the JSON Ledger API.** The v2 active-contracts endpoint filters by template and party only, so statement reconciliation (`camt.053`, `semt.002`) filters positions by account, currency, or ISIN in the client. A participant query store (PQS) would move that filtering into SQL.
- **The website is a replay.** The trade walkthrough at https://aryafi-core.vercel.app replays the tested DvP scenario and does not connect to a ledger. Its code viewer shows the real source files.

## 7. Test Coverage

`dpm test` runs 394 scripts, all passing. Coverage of the `aryafi-core` package: all 34 templates created and 183 of 250 template choices exercised (73%, including each template's implicit `Archive`). The coverage report does not count interface choices; the tests exercise all fifteen token-standard choices that AryaFi implements (`Allocation_Settle`, which AryaFi refuses, to check the refusal) and both `CompliancePolicy` choices. Property-based tests do not exist yet, and the multi-participant tests cover both DvPs, a repo agreed and rolled, a repo's legs settled, an escrow released with and without a deposit, and screened transfers (`runDvpAcrossNodes`, `runTokenDvpAcrossNodes`, `runFinancingAcrossNodes`, `runFinancingLegsAcrossNodes`, `runComplianceAcrossNodes`).

See [IMPROVEMENT_PLAN.md](IMPROVEMENT_PLAN.md) for how these limitations are addressed.
